## Objectives against what was delivered

O21 in `docs/STATUS.md` reads: "Test on a scratch database on the NAS: UNC open,
writes, locking with two PCs". The proposed default was: "The agent writes a script
that takes the path as an argument. The user runs it." The user has no NAS access at
present and asked for the parts that can run on this PC, and for a new `test.db`.

| Objective | Status | Notes |
| --- | --- | --- |
| A script that takes the database path as an argument | Done | [db_check.py](../../tools/db_check.py) with four commands: `create`, `check`, `hold`, `write`. It uses the app's code in `iqdm.db`. |
| Writes | Done, tested locally only | `check` writes a site, a recording with one channel and a `transfer_log` row through `write_transaction`, then reads them back. |
| Locking | Done, tested locally only | Two separate processes on this PC. The Milestone 1 tests used two connections in one process. |
| UNC open, locking with two PCs | Not done | Needs the NAS. The user runs the steps below. |
| A new `test.db` | Done | `dev/test.db`, created with `python tools/db_check.py create dev/test.db`. It holds the schema and no rows. `dev/` is gitignored. |

What `check` tests:

| Step | Passes when |
| --- | --- |
| database file | The file exists |
| schema version | `database_status()` is `current` |
| open read-only, check pragmas | `foreign_keys = 1` and `busy_timeout = 5000` |
| open read-write, check pragmas | Also `journal_mode = delete` |
| read-only connection refuses a write | `add_site` on a `mode=ro` connection fails with a read-only error |
| write site, recording, channel, transfer | One `write_transaction` commits all four rows |
| read back | The rows read back with the same site name, path, 1 channel and 1 transfer |

Each run of `check` or `write` uses names made from the UTC time, the PC name and a
random suffix, so the commands can repeat. Their rows stay in the database.

## Results on this PC

A manual run on a new database in a temporary folder gave these results:

- `create` and every `check` step passed. The new database is 73,728 bytes.
- `hold --seconds 10` in one process, then `write` in another: the write printed
  "database locked; retrying in 1 s" and passed after 10.0 s and 2 attempts.

The tests in [test_db_check.py](../../tests/test_db_check.py) (14) give the same
locking results with separate processes:

| Lock held | Expected | Result | Test time |
| --- | --- | --- | --- |
| 3 s | The 5 s busy timeout covers it: 1 attempt | Passed | 3.12 s |
| 8 s | 1 retry: 2 attempts | Passed | 8.19 s (slow marker) |
| 25 s | "database is busy" after 3 attempts, between 15 s and 25 s | Passed | 25.09 s (slow marker) |

## Steps for the user on the NAS

Use a scratch copy only, never the real catalogue. Open a terminal in the repository
on each PC and activate the venv (`.venv\Scripts\activate`). Replace `<NAS folder>`
with the scratch folder's UNC path.

1. Copy `dev/test.db` to `<NAS folder>`.
2. On PC A: `python tools/db_check.py check "<NAS folder>\test.db"`. Every line
   should read PASS.
3. On PC A: `python tools/db_check.py hold "<NAS folder>\test.db" --seconds 10`.
4. On PC B, within 10 s: `python tools/db_check.py write "<NAS folder>\test.db"`.
   Expected: PASS after about 10 s and 2 attempts.
5. Repeat steps 3 and 4 with `--seconds 25`. Expected: FAIL with "database busy"
   after about 18 s and 3 attempts. That FAIL is the correct result.
6. Paste the output of every step into the session for the record.

PC B needs the repository and its venv. Each command prints the PC name and the UTC
time, so the outputs of the two PCs can be matched.

## Decisions made

None. `connection_settings()` is a new helper in
[connection.py](../../src/iqdm/db/connection.py). It reads the three pragmas so that
the tool needs no SQL of its own (all SQL lives in `src/iqdm/db/`). One test covers
it in `tests/test_connection.py`.

## Changes from the plan

- **`connection_settings()` added to `iqdm.db.connection`.** The plan did not name
  it.
- **Run names use a random suffix in place of the process id.** Two `check` runs in
  one process within one second would otherwise collide on the unique site name.
- **`tools/db_check.py` imports `sqlite3` for type hints only.** D10 limits `sqlite3`
  imports to `src/iqdm/db/`. That rule applies to the package, not to `tools/`.

## Untested or not testable here

- **UNC paths and SMB locking.** Agents may not access network paths. SMB locking
  can behave differently from local locking, which is the point of O21.
- **Two PCs.** Two processes on one PC share one file system driver.

## Issues found in self-review

1. **Busy timing differs from D7's estimate.** D7 gives "about 18 s" before the
   error. The test allows 15 s to 25 s, because the second process starts a moment
   after the lock is taken. Left as is.
2. **The `schema version` line of `check` shows a time, not the status.** It passes
   only when the status is current. Cosmetic; left unchanged.
3. **A blocked command during this work.** The safety hook blocked a shell command
   that wrote a temporary folder path into `STATUS.md`, because the escaped
   backslashes looked like a UNC path. The folder is a local scratch folder under
   the user's temporary directory, made by the manual run above. It is not listed
   in `STATUS.md`; the user was asked how to proceed.
