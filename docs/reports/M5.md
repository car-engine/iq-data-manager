### Local copy timings

Measured on this PC's local disk with the first version of
[copy_check.py](../../tools/copy_check.py) (made source, flush on), with `--hash`, one
run each. They show the engine's own cost; the network sets the speed on the NAS.

| Files | 1 at once | 4 at once | 8 at once |
| --- | --- | --- | --- |
| 10 × 100 MB | 1.3 s, 761.1 MB/s | 0.5 s, 1,984.2 MB/s | 0.4 s, 2,341.6 MB/s |
| 2,000 × 0.064 MB | 17.0 s, 7.5 MB/s | 3.3 s, 39.0 MB/s | 3.0 s, 42.8 MB/s |

Checking the 2,000 small files took 10.9 to 12.1 s. A probe without hashing,
`dev/m5-copy-check/fsync_probe.py`, copied the 2,000 small files with 1 worker in
4.29 ms per file with `fsync` and 3.45 ms per file without it. The engine keeps
`fsync`.

## Changes after the user's review

The user cannot reach the NAS from the development network. A test there means
taking a frozen build to a recording laptop and reporting the next day. The user
asked about the risks of testing on the NAS only with the Milestone 6 build, then
decided on that (D54) and asked for test data that covers the cases. Commit
`9ce023e`:

- [make_nas_testset.py](../../tools/make_nas_testset.py) writes five synthetic
  recordings of random bytes, with `TESTSET.md` (what to test with each, and in which
  order) and `testset.json` (ground truth). The default set holds 5.05 GB; `--quick`
  writes 67.8 MB with the same structure.

  | Folder | Covers |
  | --- | --- |
  | `A-large-files` | 2 channels × 10 files of 200 MB: throughput, archive, cancel and resume, check, delete |
  | `B-small-files` | 2 channels × 2,000 files of 64 kB: the cost per file |
  | `C-gaps-and-ranges` | 2 channels × 300 slots of 1 MB, with gaps, channel 1 starting later: ranges, channel subsets, missing seconds |
  | `D-bin-single-channel` | 120 `.bin` files of 1 MB in the folder itself, a short last file |
  | `E-half-second-files` | 240 files of 0.5 s: fractional file names, range bounds between files |

- [copy_check.py](../../tools/copy_check.py) takes `--source DIR`, for example a
  test-set recording, and `--fsync on|off|both` (default both). Each run prints the
  time per file.
- `copy_files(fsync=False)` exists for that comparison. The app keeps the flush.
  A first run on this PC's disk, on `B-small-files` of the quick set (400 files of
  4 kB), gave 8.92 ms per file with the flush and 3.48 ms without it with 1 file at
  once; 1.78 and 1.44 ms with 4 at once; 1.45 and 1.22 ms with 8 at once. Copying
  several files at once hides most of the flush's wait.
- [make_fixtures.py](../../tools/make_fixtures.py) gains `random` content, so a NAS
  that compresses data on its disks cannot make a copy look faster.
- STATUS.md has three new open items for the Milestone 6 plan: O34 (diagnostics and
  the test set in the packaged app, because the laptops have no Python), O35 (files
  at once and the flush as settings) and O36 (deletion only after a later check).

## Changes from the plan

- **The manifest name holds the finish time** (`4b65303`). The plan named it
  `transfer-<id>.json`. Two databases on one PC that reuse a transfer id would then
  collide, and a move would fail after its copy and check (issue 2). D52 and SPEC
  section 8 now give `transfer-<id>-<time>.json`.
- **A manifest is written only after a passed verification.** The plan said after
  each copy or move. A failed or cancelled transfer has no manifest, and nothing can
  use one. D52 and SPEC say so.
- **`power.py` came with the copy engine** in `d3547c6`. It was step 10 of the plan.
- **`scan_differences` stays in `viewer.py`.** `selection.py` and `operations.py`
  import it from there. The plan allowed moving it.
- **The architecture test also bans the `shutil` copy functions in `transfer/`.**
  They replace an existing file. `Path.replace()` cannot be told from `str.replace()`
  by the test, so review covers it.
- **Two fixes beyond the plan**, found in self-review: the move destination (issue 1)
  and two moves at once (issue 3).
- **New open item O33**: long paths in the packaged app.

## Untested or not testable here

- **Throughput to the NAS, and the cost of the flush there.** Agents may not access
  network paths. The user decided to test on the NAS with the Milestone 6 build
  (D54), with the test set and `copy_check.py --fsync both`.
- **A check straight after a copy to the NAS.** Windows may serve the read from its
  cache, so the hash may compare the PC's memory with the source. "Check archive"
  rescans later. Whether the cache matters here is not measured. O36 proposes that
  deletion waits for a later check.
- **Links.** Three tests skip because this account cannot create symbolic links, as
  in earlier milestones. The code refuses links in the destination, keeps a link in
  place of a laptop file, and checks that each laptop file resolves inside its
  folder.
- **Long paths enabled.** `long_paths_enabled()` reads the registry. The tests pass
  the setting in. The packaged app needs a `longPathAware` manifest as well (O33).
- **Keep-awake.** The tests check the calls and one real call on Windows. Whether
  the PC stays awake during a long copy needs a real transfer.
- **Two PCs at once.** Two moves of one recording are tested in one process against
  one database. Locking between PCs on the NAS is O21.
- **Linux.** The engine checks for an existing target before its rename, because
  Linux would replace it. There is no Linux test run.

## Issues found in self-review

1. **A move typed with a mapped drive could not be deleted.** The log row stored
   `Z:\...` and the recording stored the UNC path, so `prepare_delete` refused.
   Fixed in `4b65303`: the preview resolves the NAS location once, and the copy, the
   row and the manifest use it. Tested.
2. **Manifest names could collide.** Fixed in `4b65303` (see "Changes from the
   plan").
3. **Two moves of one recording at once.** Both previews passed, and the second
   finish replaced the first archive location. Fixed in `57b3899`: `finish_move`
   refuses a recording that is no longer local, and the second move is logged as
   failed. Tested.
4. **A resumed file is trusted by its size.** A target file already in place with
   the source's size is skipped (D51). In hash mode `none`, or in `sample` mode when
   the file is not in the sample, a same-size file with other content passes the
   check. The engine renames a file only when it is complete, so such a file comes
   from outside the app. Left unchanged. One option for Milestone 6 is to hash every
   skipped file.
5. **Sample mode hashes every source file during the copy.** The cost is processor
   time only, while the bytes pass through memory anyway. Left unchanged.
6. **A shell edit against the agents' notes.** One rename in `manifest.py` used
   `sed -i`. STATUS.md says to change files only with the Write and Edit tools. The
   rename was checked with `grep` and is correct. Later edits used the Edit tool.
7. **A transfer row can stay unfinished after the copy.** If the database is locked
   for longer than the retries (D7) at the final write, the row keeps
   `finished_at` NULL. The files and the manifest are in place, and the recording
   stays `local`. A new move of the same selection resumes and skips every file.
   Left unchanged.
